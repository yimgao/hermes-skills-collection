# Decision Journal / 决策日志

> 把“我为什么这样选”记录在结果揭晓之前；之后用证据复盘判断质量，而不是只看输赢。

## Overview

Decision Journal 用于管理跨天、跨月的重要决定。它不替代会议纪要：会议纪要记录团队发生了什么；本 skill 维护一份可回看的决策账本，保留当时的信息集、备选方案、关键假设、信心和复盘结果。

| 能力 | 作用 | 典型场景 |
|---|---|---|
| 决策捕获 | 将模糊纠结转成结构化记录 | 选 offer、供应商、技术方案 |
| 可逆性判断 | 区分双向门与单向门 | 决定需要多快、多严谨 |
| 假设与证据 | 显式记录支持、反对证据 | 防止事后改写理由 |
| 概率校准 | 记录预测及信心 | 检查是否长期过度自信 |
| 定时复盘 | 到期比较预测与实际结果 | 提炼可复用规则 |
| 本地优先 | Markdown 文件可搜索、可迁移 | 不依赖云服务或 API |

默认数据目录：`~/.hermes/data/decision-journal/`。推荐一项决策一个 Markdown 文件，文件名为 `{YYYY-MM-DD}-{slug}.md`。可复制 [templates/decision-entry.md](templates/decision-entry.md)；字段定义见 [references/field-guide.md](references/field-guide.md)；用 [scripts/validate.py](scripts/validate.py) 做确定性检查。

## When to Use

- “帮我记录为什么选 A，不选 B，三个月后提醒我复盘。”
- “我在两个 offer / 供应商 / 架构之间犹豫，帮我做决策日志。”
- “复盘去年换工作的决定，当时哪些假设对了？”
- “统计我过去 20 个高信心预测的命中率。”
- “从会议纪要里的关键决策创建长期跟踪记录。”
- 决定有明显机会成本、影响超过一周，或结果会在未来才揭晓时。

不用于：只需立即执行的微小偏好；纯会议纪要（用 `meeting-minutes-generator`）；医疗、法律或投资结论的专业替代意见。

## Core Workflow

### Step 1：判定是否值得记录

先用四项筛选：

1. **影响**：时间、金钱、关系、职业或技术债是否显著？
2. **不确定性**：结果是否依赖尚未验证的假设？
3. **延迟反馈**：结果是否数周或数月后才知道？
4. **可复用性**：未来会遇到类似选择吗？

任意两项为“是”就建档。再分类：

- **双向门 / 可逆**：退出成本低，优先小实验和速度。
- **单向门 / 难逆**：退出成本高，要求反方证据、预演失败和明确止损线。

### Step 2：冻结“当时视角”

创建目录并复制模板：

```bash
mkdir -p ~/.hermes/data/decision-journal
cp templates/decision-entry.md \
  ~/.hermes/data/decision-journal/2026-07-25-example.md
```

填写时遵守：

- `status` 仅使用 `open`、`decided`、`reviewed`、`superseded`。
- `confidence` 为 0–100，不写“很有信心”。
- 至少列 2 个真实选项；“什么都不做”通常也是选项。
- 每个关键假设必须可证伪，并带验证信号。
- 区分 **事实**、**推断**、**偏好**；来源不明的数字不得伪装成事实。
- 记录“什么证据会让我改变主意”。这行是防止自我辩护的熔断器。

若信息不足，不替用户脑补；使用 `unknown` 或明确标注 `[待确认]`。

### Step 3：比较选项并做决定

采用加权标准，但不要把分数当神谕。流程：

1. 选 3–7 个互不重复的标准，权重合计 100。
2. 每个选项按 1–5 打分，并给一句依据。
3. 做敏感性检查：改变最大两个权重后，赢家是否变化？
4. 做失败预演：假设一年后结果很差，最可能的三个原因是什么？
5. 记录最终选择、未选方案的代价、首个下一步和止损条件。

最终输出应明确区分：

- **决策质量**：过程是否基于当时可得信息且逻辑一致。
- **结果质量**：后来是否得到好结果。

好决策可能遇到坏运气；坏决策也可能侥幸成功。不要让结果偏差劫持复盘。

### Step 4：安排复盘

选择能让主要假设显露的日期，不要机械地都设 30 天：

- 快速可逆实验：7–14 天。
- 招聘、工具或供应商：30–90 天。
- 职业、搬家等重大决定：3、6、12 个月多阶段复盘。

复盘时先遮住结论，回答：

1. 结果和当时预测分别是什么？
2. 哪些假设得到支持、被推翻、仍未知？
3. 结果中有多少来自判断、执行和运气？
4. 当时遗漏了什么信号？当时真的可知吗？
5. 下次遇到同类问题，要保留或修改哪条规则？

只追加 `## Review`，不要改写原始理由；修订用带日期的 amendment。

### Step 5：验证并周期汇总

验证单个或全部记录：

```bash
python3 scripts/validate.py \
  ~/.hermes/data/decision-journal/2026-07-25-example.md

python3 scripts/validate.py ~/.hermes/data/decision-journal/*.md
```

每月或每季度汇总：决策数量、待复盘项、平均信心、高信心错误、重复出现的失败假设。样本少于 10 个时只描述趋势，不宣称已“校准”。

## Example Invocations

### 示例 1：技术方案

**User：**“我们要选托管 Postgres 还是自己运维。记录这次决定，90 天后复盘。”

**Agent：**
> 已创建决策条目。分类为难逆但可分阶段退出。当前选择：托管 Postgres，信心 72%。关键假设：每月节省至少 18 小时运维时间；成本增量低于 $1,200；迁移不会引入不可接受的供应商锁定。改变主意的证据：压测无法满足 P95 或三年总成本超过自建 1.8 倍。复盘日：2026-10-23。未确认项已标记 `[待确认]`，没有替你捏造数字。

### 示例 2：工作 Offer

**User：**“A 工资高，B 的老板和成长更好。帮我做决策日志，不要直接替我决定。”

**Agent：**
> 我会先冻结你的标准和权重，再展示敏感性分析。当前需要确认：总薪酬、直属经理稳定性、职责边界、学习机会和最坏退出成本。输出会给出推荐区间、关键未知项和反转条件；最终选择仍由你确认。若“经理质量”权重从 25 降到 15 后赢家改变，我会明确标注此决定对个人偏好高度敏感。

### 示例 3：结果复盘

**User：**“复盘半年前选择自由职业的决定。收入没达标，是不是说明当时决定错了？”

**Agent：**
> 不能只凭坏结果判定坏决策。我会比较原始预测与实际值，拆分判断、执行和外部冲击；检查当时记录的客户转化率、现金缓冲和止损条件。若当时已有证据否定核心假设却被忽略，属于过程缺陷；若信息合理但市场突变，则主要是结果风险。原始条目保持不动，复盘作为带日期的追加段落。

## Common Pitfalls

| 问题 | 解决方案 |
|---|---|
| 结果好就认定决策好 | 分开评分“过程质量”和“结果质量” |
| 事后修改原始理由 | 原文只读；用 amendment 或 Review 追加 |
| 用精确分数伪装确定性 | 分数必须附依据，并做权重敏感性检查 |
| 所有证据都支持偏好 | 强制加入反方证据和“改变主意的条件” |
| 假设不可验证 | 改写为带指标、阈值和日期的预测 |
| 没有真实备选项 | 至少加入“维持现状/延迟决定” |
| 复盘日期太早或太晚 | 以反馈周期为准，可设置多阶段复盘 |
| 把未知信息补成事实 | 标记 `unknown` / `[待确认]`，保留来源 |
| 记录敏感隐私或凭证 | 不写密码、令牌、完整身份证件或医疗原件；必要时脱敏 |

## Verification Checklist

- [ ] 决策标题、日期、状态和复盘日期完整
- [ ] 至少两个选项，包含维持现状（若适用）
- [ ] 可逆性与退出成本已判断
- [ ] 关键标准权重合计 100
- [ ] 事实、推断、偏好已分开
- [ ] 关键假设可证伪并有验证信号
- [ ] 记录了反方证据与改变主意的条件
- [ ] 信心为 0–100，并说明主要不确定性
- [ ] 决定、下一步、止损条件明确
- [ ] 原始记录未在复盘时被改写
- [ ] `scripts/validate.py` 返回 `OK`
- [ ] 不含凭证或不必要的敏感个人信息

## Data Sources & Accuracy

- **首要数据源**：用户当时提供的事实、文档、报价、会议纪要和可验证记录。
- **外部数据**：如需薪资、价格、法规或市场数据，必须标注来源 URL、发布日期、抓取日期和适用地区；过期数据不得当作当前事实。
- **推断标记**：Agent 的估计必须标记为“推断”并给范围，不得生成虚假的确定数字。
- **概率准确性**：单个信心值不是统计事实。只有积累足够同类样本后才讨论校准，且同时报告样本量。
- **隐私**：默认本地 Markdown；提交到 Git 前先检查人名、财务、健康和雇佣信息。`.env`、`auth.json`、令牌及密码永不进入决策日志。
